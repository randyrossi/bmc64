# Hardware and Linux setup

## Rig

```text
Linux PC -- network ---------------------- BMC64
         -- USB / 3.3 V UART adapter ------ BMC64 diagnostic UART
         -- second USB / 3.3 V UART ------- Pico GP0/GP1
         -- USB HDMI capture <------------ BMC64 HDMI
                                           |
Pico USB -------------------------------- BMC64 USB host
```

The two UART links are independent. Label adapters and use stable
`/dev/serial/by-id/` paths. Use a known network address or DHCP reservation.
Keep a spare known-good SD card for recovery.

## Pico wiring

Raspberry Pi Pico (RP2040), UART0 at 115200 baud, 8N1, no flow control:

| PC-side USB-to-TTL adapter | Pico |
| --- | --- |
| TXD, 3.3 V logic | GP1 / UART0 RX, physical pin 2 |
| RXD | GP0 / UART0 TX, physical pin 1 |
| GND | GND, physical pin 3 |
| VCC / power | **Do not connect** |

Power the Pico through its USB connection to BMC64. Never connect RS-232 or
5 V UART signals. The Pico USB port is the HID connection, not the PC
control connection. See the [firmware instructions](../mock_hid/README.md).

## BMC64 diagnostic UART

Use the wiring and logging options in
[the user guide](../../../docs/USER_GUIDE.md#uart-debugging). Enable UART
logging before a test; capture from before boot when investigating startup.
UART output is 115200 baud. Logging can perturb timing, so do not treat a
log-heavy smoke run as a performance benchmark.

## Identify the adapters

```sh
ls -l /dev/serial/by-id/
```

If unsure which adapter is which, unplug only the PC-side USB UART adapter
connected to the Pico, repeat the listing, and identify the missing entry.
Reconnect it and use its stable path. Leave the Pico's USB HID connection
to BMC64 connected.

If stable names are unavailable, discover numbered devices with:

```sh
ls -l /dev/ttyUSB* /dev/ttyACM* 2>/dev/null
```

Numbered names can change after reconnecting. Only one process may own each
UART; close serial terminals before running the smoke test.

## HDMI video

The validated dongle is USB `534d:2109`, MacroSilicon MS2109. Its stable
video path is `/dev/v4l/by-id/usb-MACROSILICON_2109-video-index0`.
Other devices/revisions may differ. Do not assume the first webcam or the
same numbered `/dev/videoN` on every PC is the HDMI input.

After configuration, close VLC/OBS and other capture processes, then run
from `tools/automated_release_testing/`:

```sh
./run_video_test
```

This opens FFplay using the video device in `test_setup.json`. You can start
the preview before manually powering on the Pi and check that its boot
display appears. The script does not switch power, reset/autostart the
guest, access UART/HTTP, or capture audio. Press Q or close the window before
running `./run_tests`; both must not own the video device simultaneously.
The helper is supplied with the tools, not generated by configuration.

For a different device or before saving a setup:

```sh
./run_video_test --video /dev/v4l/by-id/YOUR_CAPTURE_DEVICE
```

Whether opening capture before boot affects the Pi's HDMI initialization
depends on the hardware and is not established by this tool. A visible
preview is an operator check, not an automated assertion.

The equivalent manual FFplay command is:

```sh
ffplay -f v4l2 \
  -input_format mjpeg -video_size 1280x720 -framerate 30 \
  -fflags nobuffer -flags low_delay -framedrop -an \
  -i /dev/v4l/by-id/usb-MACROSILICON_2109-video-index0
```

This is a video-only preview. The requested 30 fps is not a measurement of
physical HDMI timing; capture negotiation, buffering and frame loss can
differ. Preview latency and A/V synchronization are not certified.

Enumerate formats using the actual device path:

```sh
ffmpeg -f v4l2 -list_formats all \
  -i /dev/v4l/by-id/usb-MACROSILICON_2109-video-index0
# Optional, if v4l2-ctl is installed; includes frame intervals:
v4l2-ctl -d /dev/v4l/by-id/usb-MACROSILICON_2109-video-index0 --list-formats-ext
```

FFmpeg's format-listing command normally exits with an error after printing
formats; that alone does not mean the device failed.

## HDMI audio

List capture hardware:

```sh
arecord -l
```

The validated dongle uses ALSA `CARD=MS2109,DEV=0`. Prefer its card name over
a changing numeric card index. Do not accidentally select a webcam microphone.
With the BMC64 producing known sound, listen through the PC:

```sh
ffplay -nodisp -f alsa -i plughw:CARD=MS2109,DEV=0
```

Start with the PC playback volume low. `plughw` permits ALSA format
conversion. To inspect another device's native parameters, replace the
card/device placeholders:

```sh
arecord -D hw:CARD,DEVICE --dump-hw-params -d 1 -t raw /dev/null
```

Close audio playback/capture processes before the automated test. The
validated recording configuration is MJPEG 1280x720 plus 48 kHz stereo PCM;
the runner saves the combined recording and analyses a mono copy of audio.

HDMI capture does not test analogue audio. Analogue testing requires an
appropriate stereo line input, not a microphone-only adapter.

## Validation boundaries

The [C64 smoke test](smoke-test.md) is validated on Pi3A+ C64 PAL. The Pico
enumerates as keyboard, mouse and gamepad; keyboard input, held Space and
automatic release have been checked. Mouse/gamepad routing, modifiers,
reconnect behaviour and HDMI no-signal handling are not qualified by this
smoke test.

There is no automatic power or SD-card recovery. Do not power-cycle during
normal SD writes or updates, or allow PC and target to access one SD card
simultaneously.
